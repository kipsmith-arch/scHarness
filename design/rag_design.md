# RAG 设计文档(经验库 / LLM 笔记本)

## 0. 定位(重定位 v2)

RAG 从"skill 的决策点检索"收敛为一个**loop 内置的通用笔记本**(跨会话记忆):

- **它是 loop 自带工具,不是 skill 工具**。skill 完全无感知——既不知道有笔记本,也不决定它的内容。
- **完全被动**:loop 不自动注入任何记忆;只有 LLM 显式调用工具时才读写。
- **记录什么、何时记录、何时查询,由 LLM 自己决定**。loop 只在系统提示里给通用用法提示,不解析笔记内容。
- **领域无关**:笔记内容是任意文本(LLM 爱写什么写什么),loop 只负责存、embed、检索。换任何 skill 都能用。

### 与 v1 的变更(砍掉/改动)

| v1 内容 | 处置 | 原因 |
|---|---|---|
| 增益 A:决策点知识检索(knowledge/*.md 分块 + 决策点路由表 + 两段式检索) | **砍掉** | 与 skill 强耦合(决策点、SOP、指标解读全是 skill 领域语义) |
| 增益 B:run_log case 构造 + 决策点硬过滤 + 指标路径对齐 | **砍掉** | 结构化 case 依赖 skill 的 judgment 字段(decision_point/inputs/output) |
| judgment 的 `retrieved_refs` 字段 | **砍掉** | 绑定决策点语义 |
| R1/R2/R3 消融(基于 B1 决策点三臂) | **改为 N1/N2/N3**(通用,见 §7 / `experiment_design.md` §4.4) | 笔记本与决策点解耦,评估也解耦 |

保留的只有一条:把历史经验变成可检索的记忆,复用"上次遇到类似情况怎么处理的"。

## 1. 架构总览

```
┌──────────────────────────── Loop(通用)────────────────────────────┐
│                                                                    │
│  系统消息 = loop 通用提示(含笔记本用法指导) + skill.system_prompt     │
│                                                                    │
│  ┌─────────────┐   tool_calls   ┌──────────────────────────────┐  │
│  │     LLM     │ ─────────────→ │ Tool dispatcher               │  │
│  │ (OpenAI FC) │                │  ├─ skill 工具(subprocess/    │  │
│  │             │ ←── result ─── │  │    function)               │  │
│  └─────────────┘                │  └─ loop 内置笔记本工具:       │  │
│       │                         │      write_note / retrieve_notes│ │
│  no tool_calls → END            └──────────────┬───────────────┘  │
│                                                │                  │
└────────────────────────────────────────────────┼──────────────────┘
                                                 ▼
                                  笔记存储 notes.jsonl + Chroma 向量索引
                                  (路径见 §4,默认共享目录)
```

- **loop 的新职责**:注册两个内置工具、把笔记本用法指导拼进系统提示、提供笔记存储路径。仍是"领域无关"——不知道也不解析笔记内容。
- **skill 的职责不变**:只提供 system_prompt + 工具 + 日志。笔记本对 skill 透明。

## 2. 工具接口(loop 内置)

两个 `function` 类型工具,由 loop 的 dispatcher 直接注册(不在 skill 的 `tool_runtime` 里)。

### 2.1 write_note

```json
{
  "name": "write_note",
  "description": "在跨会话笔记本中写一条笔记(经验/判断/教训)。笔记持久化,后续会话可用 retrieve_notes 检索到。",
  "parameters": {
    "type": "object",
    "properties": {
      "content": {
        "type": "string",
        "description": "笔记正文。建议句式:'什么情况 → 做了什么 → 结果/理由',便于日后检索与复用。"
      },
      "tags": {
        "type": "array",
        "items": {"type": "string"},
        "description": "可选标签,便于按类检索,如数据集名、事件类型、器官等。"
      }
    },
    "required": ["content"]
  }
}
```

### 2.2 retrieve_notes

```json
{
  "name": "retrieve_notes",
  "description": "按语义相似度检索历史笔记。做重要判断前、遇到异常/未知情况、开始新任务时建议查询。",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "检索意图,用当前情境描述(指标形态/遇到的问题/正要做的决定)。"
      },
      "tags": {
        "type": "array",
        "items": {"type": "string"},
        "description": "可选,限定在带这些标签的笔记里检索。"
      },
      "top_k": {"type": "integer", "default": 5}
    },
    "required": ["query"]
  }
}
```

### 2.3 返回契约

write_note 返回 `{"status":"ok","data":{"note_id":"note-0001"}}`。
retrieve_notes 返回:

```json
{"status": "ok", "data": {
  "notes": [
    {
      "note_id": "note-0001",
      "content": "silhouette=0.15 时先别急着调分辨率,查是否发育连续谱;重跑 res 0.8→0.6 后 0.32,accept",
      "tags": ["clustering_quality", "SRP171040"],
      "ts": "2026-08-04T14:00:00Z",
      "session_id": "sess-...",
      "score": 0.87
    }
  ]
}}
```

失败返回 `{"status":"error","error":...}`,与既有工具契约风格一致。

## 3. 存储与索引

### 3.1 笔记格式(notes.jsonl,NDJSON)

```json
{"note_id": "note-0001", "ts": "2026-08-04T14:00:00Z", "session_id": "sess-...", "project_id": "SRP171040", "tags": ["clustering_quality"], "content": "..."}
```

一条笔记 = 一个检索单元。粒度由 LLM 控制:一条可复用的判断/经验写一条,过长时 LLM 自会拆开(工具描述里引导)。

### 3.2 存储位置与共享

- 路径优先级:环境变量 `RAG_NOTES_DIR` > `<project_dir>/notes.jsonl`。
- 设了 `RAG_NOTES_DIR`(如一个跨数据集的共享目录)时,所有会话共享同一笔记本 → **跨数据集经验复用**;不设时笔记只在该 project 内可见。
- 遵循 tool_design.md §10 环境变量原则,不硬编码路径。

### 3.3 向量索引(**Chroma** 持久化向量库,实施定版)

- **架构**:`notes.jsonl` 仍是权威存储(可审计、loop 不解析);Chroma persistent 向量库是它的**追加式投影**——`write_note` 双写(jsonl + Chroma upsert),`retrieve_notes` 查询 Chroma。
- **存储位置**:Chroma 数据目录 = `notes.jsonl` 同目录下 `notes_chroma/`(跟随 `RAG_NOTES_DIR` 共享,天然支持跨数据集经验复用)。
- **嵌入向量**:自定义 EmbeddingFunction 复用可插拔的本地 `sentence-transformers`(默认 `all-MiniLM-L6-v2`,本地缓存优先、离线安全),通过 `RAG_EMBEDDING` 指定(`off`/`none`/`bm25` 则完全禁用向量索引)。
- **元数据过滤**:每条笔记的 tags 以 list 存入 Chroma metadata,查询时用 `$contains` 做单/多标签过滤(AND)。
- **一致性**:集合带 `index_version`;检索前若 `count()` 与 jsonl 行数不一致(手工编辑/索引丢失),自动重建(笔记量级几十~几百条,重建成本低)。
- **冷启动兜底**:Chroma / embedding 任一不可用(未装、模型未缓存、网络断)时,退回关键词匹配(BM25 式,基于 jsonl),保证工具不失效。

## 4. 记录/查询时机(设计讨论)

> 这是定位里唯一需要"设计决策"的部分:loop 系统提示给什么指导、指导到什么粒度。原则:**只给启发式,不写死规则**——时机判断最终由 LLM 自主,loop 不强制、skill 不参与。

### 4.1 记录时机(候选,按价值排序)

| 时机 | 记什么 | 价值 | 推荐 |
|---|---|---|---|
| **改主意/重跑后** | v1 判断 → 重跑后指标 → v2 判断 | 最高:"什么信号预示该重试/调整"是可复用性最强的经验 | 强提示 |
| **发现异常/反直觉案例** | 如"sil 低但发育连续谱正常,没重跑" | 高:这类笔记是检索召回最有用的一类 | 强提示 |
| **重要判断后** | 核心指标形态 → decision → 一句理由 | 高:形成"判断经验库" | 强提示 |
| **session_start** | 数据集、组织、目标、已知概况 | 中:后续检索的锚点,便于按数据集找经验 | 提示 |
| **session_end** | 复盘:整体结论 + 教训 | 中:给未来会话留参考 | 提示 |

### 4.2 查询时机(候选)

| 时机 | 查什么 | 推荐 |
|---|---|---|
| **开始新任务/新数据集** | 历史同类任务的笔记(可带 tags 过滤) | 强提示 |
| **做重要判断前** | 用"当前指标形态"作 query 查类似历史判断 | 提示(不强制,由 LLM 判断可比性) |
| **遇到 unknown/异常/首次面对的情况** | 历史怎么处理 | 强提示 |
| **准备重试/调参前** | 历史参数调整经验 | 强提示 |

### 4.3 讨论要点

1. **完全被动 vs 半自动**:用户明确"完全被动,由 LLM 调用"。风险是 LLM 自觉性不足、使用率低。缓解:系统提示足够强调(§5 文案),并在评估 N2 里统计使用率——若过低再考虑加强提示强度,而非改成主动注入。
2. **记录粒度**:一条可复用判断记一条;太细(逐条指标)会稀释检索、太粗(整场会话)则检索不精准。工具描述里引导"可复用的判断单元"。
3. **笔记是否携带领域知识**:会——LLM 记的笔记必然涉及细胞类型等生物语义。这正是解耦点:**loop 存取但不解析,知识语义完全由 LLM 拥有**。
4. **失败会话污染**:笔记可能来自失败 session,也可能误导。缓解:笔记带 `session_id` 可溯源;系统提示强调"仅供参考,独立判断"。
5. **过期/漂移**:按 `ts` 排序,检索结果可标注新旧;tag 便于人工/LLM 清理。

## 5. Loop 系统提示中的笔记本指导(通用文案)

loop 拼系统消息时,把这段(或类似)放在 skill 提示之前。**不含任何领域词**,换 skill 通用:

```
你有一个跨会话的"笔记本"(持久化记忆)工具,用于记录与复用经验:

- 记录(write_note):完成重要判断、发现可复用经验或教训、改主意时,
  用一句话记下"什么情况 → 做了什么 → 结果/理由"。反直觉案例(结果与
  直觉相反但正确的)尤其值得记。
- 查询(retrieve_notes):开始新任务、做重要判断前、遇到异常/未知情形、
  准备重试或调参前,先查历史笔记,看是否有可借鉴的处理方式。
- 笔记可能来自过去的会话(含失败会话),仅供参考,必须结合当前数据
  独立判断,不要盲从。
```

skill 的系统提示**不提到笔记本**。两者物理拼接:loop_base_prompt + skill.system_prompt。

## 7. 评估(通用,不绑决策点)

| 实验 | 对比 | 指标 |
|---|---|---|
| **N1 笔记本开关消融** | 笔记本可用 vs 禁用(工具注册但系统提示禁用它) | 端到端质量:细胞级 strict/relaxed(见 `eval_design.md`)、unknown_rate;判断稳定性 |
| **N2 使用分析** | — | write_note / retrieve_notes 调用次数与时机分布、笔记主题分布、top-k 相关性抽查、检索结果是否被采纳(人工抽查后续 LLM 输出是否体现笔记内容) |
| **N3 工具本身验证** | 换最小 skill(如 echo) | 证明笔记本是 loop 级通用能力,与 skill 无关 |

- N1 与 skill 无关,可在真实 skill 上跑;结论表述为"通用记忆模块对判断质量的增益",不绑定决策点。
- N2 的"使用率"是关键:若 LLM 几乎不调用,先治提示强度,再谈增益。

## 8. 实施计划

| Phase | 内容 | 依赖 | 产出 |
|---|---|---|---|
| M-1 | `write_note` / `retrieve_notes` 工具 + notes.jsonl 存储 + **Chroma 向量索引**(含 BM25 兜底) | loop 本体(L-1) | 笔记本内核 |

## 9. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| LLM 不主动用笔记本,模块空转 | 无增益还多两个工具 | 系统提示强调 + N2 统计使用率;过低则加强提示,而非改主动注入 |
| 失败会话的笔记误导后续判断 | 质量下降 | 带 `session_id` 可溯源 + 提示"仅供参考,独立判断" |
| 笔记语义漂移/过期 | 检索到过时经验 | 结果带 `ts`,按时间排序可选项 |
| embedding 依赖不可用 | 工具失效 | Chroma 不可用时 BM25 兜底 + `RAG_EMBEDDING` 可插拔(默认本地缓存模型,离线安全) |
| 与 loop"极简"哲学冲突 | 架构漂移 | 显式决策:loop 仍是领域无关,只是多一个通用记忆能力;在 loop_design.md 明示并让 N3 证明通用性 |

---

## 10. 定位总结

一句话:**RAG = loop 内置的、完全被动的、领域无关的 LLM 笔记本**。它把"经验复用"从 skill 的决策流程中剥离出来,变成 loop 层的通用能力——skill 不感知、loop 不解析、内容全归 LLM。这才是与既有三层架构(loop/skill/pipeline)一致的位置。
